Architecture Reference

OSS CPQ Architecture

The authoritative reference for OSS Configure Price Quote (CPQ). CustomCall is the billing system and product catalog — the system of record for item codes, base attributes, recurring charges, and MACD activity on billing items. OSS is the order processing system — it wraps the package construct around CustomCall items, processes orders, and feeds provisioned items back to CustomCall for billing.

00

Solution Journey

Every solution journey begins with Internet as the root service. The first decision — who supplies the internet circuit — acts as a gate that shapes which sub-packages and options are available downstream. Both NHC supplied and customer supplied internet can lead to routing, SD-WAN, or security options, but certain combinations limit the path forward. Selecting a customer-supplied router, for example, may terminate further sub-package options beneath it. Each choice either opens or narrows the path. The service termination point — where NHC's obligation for that branch is fully defined — can occur at the core package level or deeper, depending on what is selected.

①
Internet is always the root service
Every solution journey in this context begins with Internet as the core service package. The anchor item carries the primary service charge. Internet is the entry point — all routing, SD-WAN, and security options are sub-packages within or alongside it.
②
First gate: who supplies the internet?
The first choose-one decision is NHC supplied or customer supplied internet. Both paths lead to routing options, but the supply choice may limit what is available downstream. NHC supplied internet typically opens the broadest set of sub-package options; customer supplied may restrict certain managed service options.
③
Second gate: routing and edge device
Within the internet supply choice, the next decision is the edge device — Managed Router, SD-WAN, Security device, or Customer Supplied Router. NHC managed options open the deepest sub-package paths. A customer-supplied router is valid on either internet supply type but may terminate further sub-packages beneath it.
④
Each choice opens or closes paths
Every selection either opens downstream sub-packages or terminates the path. Customer-supplied router with NHC internet is valid, but sub-packages that require NHC-managed hardware will not be available. The service termination point — NHC managed, carrier, or customer infrastructure — can occur at any level. It is a boundary, not necessarily a dead end.
01

Package Library

Every package is created as a standalone object in the library — independent of where or how it will be used. Its content (items, amounts, flags) is defined once. Its role is then assigned separately. The same package can be a top-level product, an internal building block, or both at the same time.

Top-level
The package appears in the library and can be selected directly by NHC sales and quote personnel as the starting point for a solution journey.
internal: false
Internal sub-package
The package is hidden from the top-level library. It exists solely as a building block — linked as a sub-package inside one or more parent packages.
internal: true
Both
The package appears at the top level AND is linked as a sub-package inside other packages simultaneously. The same object serves both roles.
internal: false + linked
02

Structure

A top-level package is a container. It holds an anchor item (which carries the core service charge), direct items (fixed, optional, or choose-one), and one or more sub-packages. Sub-packages are self-contained, reusable building blocks that can be nested to any depth and linked to multiple parent packages simultaneously. Every item at every level carries its own amount — all selected amounts accumulate into a monthly total.

Anchor item
The anchor item shares its code with the parent package. It is always required, always locked (cannot be deactivated by any parent override), and carries the core service charge for that package.
Sub-packages
Sub-packages marked internal do not appear at the top-level library view — they exist only as building blocks inside parent packages. The same sub-package can be linked to multiple parents simultaneously.
Amount accumulation
Every selected item contributes its amount to the monthly total. Optional items multiply qty × unit price. Sub-package items each carry their own individual amounts — there is no single "sub-package price".
Choose-one groups
Items sharing the same coGroup string form a mutually exclusive group. The customer picks exactly one. A default flag pre-selects one option. Sub-packages can also form a choose-one group at the parent level.

Limitations

Hard constraints are enforced by the system at save time and cannot be bypassed. Design constraints are architectural conventions — the system will not prevent them, but violating them will produce unexpected behaviour.

05

Deal Margin & Financial Model

The package construct defines what is sold and what it costs the customer. The financial model defines whether the deal is viable — covering pricing floors, commission and SPIF structures, margin calculation, and the gates that must be passed before a quote can be issued or an order placed. This model applies across quoting, ordering, supplements, and MACD activity.

5.1

Item codes and base attributes originate in CustomCall — the system of record. OSS enriches those items with the CPQ-specific financial attributes below. These enrichment attributes are currently missing from OSS — today they are managed in a spreadsheet and keyed manually at order time. Building them into OSS is the foundational fix this model depends on.

5.3

Deal Gates

Two financial gates must pass before a quote can be issued. Both are evaluated continuously during configuration — not only at submission.

5.4

Margin Calculation

Formula
deal_revenue = Σ (item_price × qty)
deal_cost   = Σ (item_cost × qty)
deal_comp   = Σ (item_price × qty × comp%)
deal_spif   = Σ (item_price × spif_mult)

gross_margin = (revenue − cost) / revenue
net_margin  = (revenue − cost − comp − spif) / revenue
Rules
Margin is calculated at the deal level — not per item or per package.

Override-repriced items use the override price in that deal context.

Items with commissionable: false contribute to revenue and cost but not comp or SPIF.

SPIF is a one-time payout — shown as a deal-level cost, not recurring.

Install margin is shown separately alongside recurring margin.
06

Quote Request Engine

The Quote Request Engine is the workflow layer that sits on top of the CPQ architecture. It governs how deals move through stages, which roles own each stage, what gates must pass before advancement, and how approvals and notifications are triggered. When a deal is won, OSS processes the order and feeds the provisioned items back to CustomCall for billing. MACD activity on those billing items is governed by the package construct rules defined in this document.

CM — Channel Manager
Owns deal creation and initial configuration. Selects core package and navigates the solution journey. Sees ICB and margin gates in real time during configuration.
SE — Sales Engineering
Auto-triggered on complex service types — SD-WAN, Security. Validates technical specifications and feasibility. Required sign-off before deal can advance to contract.
QD — Quote Desk
Reviews and issues the formal quote. Validates that all CPQ gates have passed. Cannot issue a quote if ICB violations or margin blocks are unresolved.
Orders
Auto-populated when a deal is marked Won. Receives the resolved package configuration and item codes for fulfilment. Item codes flow back to CustomCall.
CPQ gates enforced by the engine
Cannot advance to quote: ICB violation unresolved or margin hard block.

Cannot advance to contract: SE sign-off pending on SD-WAN or Security products.

Cannot place order: Quote approval not logged.

MACD blocked: Package construct rules prevent the requested change — locked items cannot be disconnected independently of their package.

The CPQ architecture (Sections 00–05) defines the rules the engine must enforce. The engine's own workflow design is a separate deliverable that references this document as its data and rules layer.
07

Project Phasing

None of this architecture is currently in place. The following phasing is recommended based on the dependency order of the constructs defined in this document. Phases 1 and 2 are foundational — nothing in Phase 3 onwards can be built accurately without them. Phases 3 and 4 can begin in parallel once Phase 2 is sufficiently populated. The pending decisions in Section 08 must be resolved before Phase 4 development begins.

Phase 1 — Foundation
Must happen first. Everything depends on this.

1. CustomCall item audit
Inventory every item code. Identify gaps in base attributes. Flag items missing cost and pricing data. This is the single most important first step — nothing else can be built accurately without it.

2. OSS data model
Build the package object, item object, and all financial attributes defined in this document. Schema work only — no UI yet.

3. Commissionable label taxonomy
Agree and define the commission bucket names with the commission team. Unblocks agent table build and catalog enrichment simultaneously.
Phase 2 — Catalog enrichment
Runs alongside Phase 1 tail. Start with highest volume packages.

4. Term pricing population
Migrate spreadsheet pricing into OSS per item per term.

5. ICB population
Finance sets ICB floors per item per term.

6. Cost basis population
Finance populates NHC cost per item per term from vendor contracts.

7. Agent table build
Commission team builds agent commission rows with term-based rates per bucket.
Phase 3 — Package construct
Can begin once data model exists and catalog is partially populated.

8. Package builder UI
Build the package manager. Real data, not mock.

9. Core packages
Build Internet, Managed Router, SD-WAN, Security using real CustomCall item codes.

10. Solution journey configuration
Wire choose-one groups, sub-package nesting, and the NHC / Customer supply gate for Internet.
Phase 4 — CPQ engine
Pending decisions (Section 08) must be resolved first.

11. Pricing resolution
Term selection drives item price. Override repricing in context.

12. ICB gate
Real-time validation. Surface violations during configuration, not at submission.

13. Margin calculator
Live gross and net margin. Comp and SPIF from agent table.

14. Margin gates
Healthy / at-risk / block thresholds. Approval workflow for below-floor deals.
Phase 5 — Quote Request Engine
Requires Phase 4 gates to be operational.

15. Stage model
Configure → SE Review → Quote → Contract → Orders.

16. Role-based views
CM, SE, QD, Orders each see their stage.

17. SE auto-trigger
SD-WAN and Security route to SE queue automatically.

18. Approval workflows
ICB exception, margin approval, SE sign-off. All logged.

19. CustomCall feed
Provisioned items flow to CustomCall for billing on Won.
Phase 6 — MACD
Requires Phases 4 and 5 to be operational.

20. MACD rules enforcement
Package construct rules applied to in-life billing item changes in CustomCall. Locked items protected. Supplement journey follows the same CPQ path as a new quote — same gates, same approvals, same package construct rules.
08

Pending Decisions

The following items require business and finance sign-off before development can be finalised. Data structures are designed to support any of the options below without redesign. These are explicitly parked — do not implement until decisions are confirmed.

✓ Resolved — Item pricing model
Decision: Pricing attributes live on the catalog item and are shared across all packages that include that item. There is no package-level price override.

Rule: If the same service component requires a different price structure in a specific package context, a new item code is created. The package override model handles contextual deactivation and flag changes only — not pricing differences.

Impact: Simplifies the data model. Catalog is the single source of truth for pricing. Price changes propagate automatically to all packages.
Does margin cap comp and SPIF payout?
Option A — Margin is a gate only
Term rate is always paid if the deal is approved. Margin determines approval, not payout size.

Option B — Margin is a ceiling
Term sets the target rate. Available margin sets the maximum that can actually be paid.
Payout = min(term rate, margin-available rate).

Decision required: Finance / Commission team
When margin is thin — what gets cut first?
If Option B above is selected and available margin cannot cover both full comp and full SPIF:

• SPIF cut first, comp protected
• Comp cut first, SPIF protected
• Both reduced proportionally
• Manual decision by approver

Decision required: Finance / Commission team
Should ICB factor in max comp and SPIF exposure?
Currently ICB = cost + minimum margin floor (independent of comp/SPIF).

Alternative: ICB = cost + max comp exposure + max SPIF exposure + minimum margin floor.

Trade-off: higher ICB floors guarantee deal viability at any payout but may reduce pricing competitiveness.

Decision required: Finance / Product
Confirmed margin thresholds
Current placeholders (from deal calculator):

• Healthy: ≥ 28%
• At risk: 15–27%
• Below floor: < 15%
• Hard block: < 0%

These may need to vary by service type or commission bucket.

Decision required: Finance

R13 Item Pricing Model — Catalog Ownership

This is a resolved architecture decision. The pricing attributes on an item are catalog-level — they apply wherever that item appears across all packages. There is no package-level price override. Price differences between service contexts require a new item code.

ScenarioCorrect approach
Same component, same price, used in multiple packages One item code. Add to each package independently. Price is consistent everywhere.
Same component, different price in a specific package context Create a new item code. Do not use package override to change price. Override is for flags only.
Price change on an existing item Update the item in the catalog. Change reflects across all packages that include it.
Deactivate or hide an item in a specific parent package Use the parent override model (R7). This is the correct use of overrides.
Change req / quoteReq / deliveryReq in a specific parent package Use the parent override model (R7). Flag overrides are valid at the package level.
Override boundary: The package override model (R7) handles contextual deactivation and flag changes only. It does not handle price differences. Price differences between service contexts = new item code in the catalog.
Catalog impact: When a carrier or vendor changes pricing, update the item once in the catalog. The change propagates to all packages that include it. This is the intended behaviour — catalog is the single source of truth for pricing.
